# 千问嵌入后刷新导致闪烁 — 诊断记录

## 现象
嵌入千问 (www.qianwen.com → tongyi.aliyun.com) 到 iframe 后，页面持续刷新。
每次刷新内容脚本重新注入，`_chatfree_injection_id` 不同，说明是整页导航而非 SPA DOM 变更。

## 实验记录

### 实验 1: MAIN-world 导航追踪
**日期**: 2026-05-17
**假设**: 内容脚本在 isolated world 中劫持 `window.location` 可能劫持不到页面主世界的导航调用（特别是 `location.reload()`、`location.replace()`、`location.assign()`）。
**方法**: 通过 `<script>` 标签注入代码到页面主世界，劫持所有导航 API：
- `location.reload()`
- `location.replace(url)`
- `location.assign(url)`
- `location.href` setter（通过 `Location.prototype`）
- `history.pushState / replaceState`
- `beforeunload` 事件兜底
每次记录带上 stack trace，写入 `localStorage:chatfree_main_nav_trace`。
内容脚本在注入前先读取上一页留下的 trace，通过 debug log 输出。
**代码变更**: `modules/content-core.js` — 新增 `injectMainWorldNavTracer()`，页面初始化时调用。
**验证步骤**:
1. Reload extension
2. 打开/刷新 ChatFree 页面
3. 打开 Debug 面板，观察 `[NAV] PREVIOUS PAGE MAIN-WORLD NAV TRACE:` 行
4. 点击 Test 按钮，观察实时 `MAIN-world nav trace (live):` 行
**结果**: 
- MAIN-world 追踪每次都是空白：`No MAIN-world nav trace from previous page`
- 注入的 `<script>` **没有执行**。最可能原因：千问页面有 `<meta http-equiv="CSP">` 或 Trusted Types 限制
- 每次 `beforeunload` 在 isolated world 正常触发，说明页面确实在导航
- 但导航的调用栈无法从 isolated world 捕获
- 刷新间隔不规则：~10s → ~1s → ~6s，不像定时器，更像错误恢复或竞争条件

### 实验 2: 验证 MAIN-world 脚本注入是否成功
**日期**: 2026-05-18
**假设**: 实验 1 中 MAIN-world trace 为空是因为 `<script>` 注入被阻止（meta CSP、Trusted Types 等）
**方法**:
1. MAIN-world 脚本第一行在 `<html>` 上设置 `data-chatfree-mainworld="1"` 属性
2. 每次 `record()` 调用同时写入 `data-chatfree-nav` DOM 属性（不受 localStorage 限制）
3. 使用 `trustedTypes.createPolicy` 兼容 Trusted Types
4. 记录 script:boot 事件到 localStorage（含 Trusted Types 状态）
5. 内容脚本在 init 时检查这些 DOM 标记
**验证步骤**:
1. Reload extension
2. 打开/刷新 ChatFree 页面
3. 在 Debug 面板搜索 `data-chatfree-mainworld` 和 `data-chatfree-nav`
4. 如果显示 `(MISSING)` — 注入被阻止，需要找出阻止原因
**结果**: 
- 千问 + 豆包 **都** `(MISSING)`，注入的脚本在所有网站都无法通过 `textContent` 执行
- 问题不在于千问特有的反嵌入，而是 `textContent` 赋值本身被浏览器/CSP 阻止

### 实验 3: Blob URL 注入 + isolated world DOM 对照
**日期**: 2026-05-18
**假设**: `textContent` 注入被 CSP `script-src` 限制（不允许 `unsafe-inline`）。Blob URL 作为独立源可能绕过。
**方法**:
1. 优先用 `new Blob([source])` + `URL.createObjectURL` 作为 `script.src`
2. 失败回退到 `textContent` + Trusted Types
3. 同时从 isolated world 直接写 `data-chatfree-isolated-test` 属性，证明 DOM 操作没问题
4. MAIN-world 脚本成功后写 `data-chatfree-inject-ts`
5. 劫持方式改为全部通过 `Location.prototype`（而非 `window.location` 属性赋值）
6. 新增 `document.location` setter 劫持
**验证步骤**:
1. Reload extension

### 实验 4 结论：根因确定！

**根因找到：千问的登录态检测 `syncLoginState`。**
Stack trace 精准显示调用链：
```
navigateAfterLogout (main.js:72:122079)
  ← x.syncLoginState (main.js:72:125924)
    ← eQ (core-libs.js:257:269542)
      ← x.syncLoginState (core-libs.js:257:269085)
```

**机制**：iframe 跨域加载千问 → 第三方 cookie 受限 → 千问读不到登录 cookie → `syncLoginState` 判定未登录 → `navigateAfterLogout` 触发页面刷新 → 刷新后仍然未登录 → 无限循环。

**关键发现**：`Location.prototype` 的覆盖在 Chrome 中不生效。只有 `history.replaceState` 被捕获到，`location.reload/assign/replace/href` 全部绕过。需要更强的拦截方式。

### 实验 5: Block 模式 — 4 路并行拦截 + self-test
**日期**: 2026-05-18
**假设**: Chrome 不允许对 Location.prototype 做简单赋值覆盖，但 `Object.defineProperty` 可能更强力。同时尝试 `window.location` setter 和 `document.location` setter 作为补充。
**方法**（2 秒后安装 blockers，让初始重定向先通过）:
1. `Object.defineProperty(Location.prototype, 'reload', {value: noop})`
2. `Object.defineProperty(Location.prototype, 'replace', {value: noop})`  
3. `Object.defineProperty(Location.prototype, 'assign', {value: noop})`
4. `Object.defineProperty(Location.prototype, 'href', {set: noop})`
5. `Object.defineProperty(window, 'location', {set: noop})`
6. `Object.defineProperty(Document.prototype, 'location', {set: noop})`
7. `beforeunload` 中调用 `preventDefault()` + `returnValue = ''`
每条拦截记录成功/失败状态到 trace
8. Self-test：注入前验证 `Location.prototype` 是否可写
**验证步骤**:
1. Reload extension
2. 打开 Debug 面板，观察：
   - `nav-guard:self-test` — Location.prototype 是否可写
   - `nav-guard:blocker-*-ok/FAIL` — 各路拦截是否成功
   - `BLOCKED:*` — 被拦截的导航调用
3. 看千问是否停止闪烁
**结果**: 
- `Location.prototype writable=true` — **`Object.defineProperty` 成功覆盖了 Location.prototype！**
- `nav-guard:blocker-reload-ok` — reload 拦截成功
- 千问**停止刷新**（log 中 47 秒内没有任何 QIANWEN beforeunload）
- 消息发送到千问成功（trySend Enter worked）
- **但** 三个副作用：
  1. 登陆框弹出（iframe 中第三方 cookie 不可用）
  2. `beforeunload` + `e.returnValue` 导致 "是否离开本面" 弹窗（Chrome 不允许静默阻止导航）
  3. 登陆后 API 调用失败（cookie 仍未发送）

**结论**: 阻止导航只能止住闪烁，不能解决根本的 cookie/auth 问题。需要注入 cookie。

### 实验 6: Cookie 注入（根治）
**日期**: 2026-05-18
**假设**: 千问在 iframe 中读不到 cookie 是因为 Chrome 第三方 cookie 限制。通过 `chrome.cookies` API 读取 cookie，再用 `declarativeNetRequest` 注入为请求头，可以使 iframe 中千问表现为"已登录"状态。
**方法**:
1. `background.js` 启动时读取千问相关域名的全部 cookie
2. 拼成 `Cookie` header，通过 `declarativeNetRequest.updateSessionRules` 动态注入
3. 监听 `chrome.cookies.onChanged` 实时更新
4. 每 5 分钟定时刷新
5. 覆盖 `sub_frame`、`xmlhttprequest`、`script`、`main_frame` 资源类型
6. 移除 `nav-guard.js` 中 `beforeunload` 的 `returnValue`（避免弹窗）
7. 同时为 doubao、deepseek、chatgpt、gemini 添加相同的 cookie 注入
**代码变更**:
- `background.js` — 新增 cookie 注入系统
- `modules/nav-guard.js` — 移除 beforeunload 的 returnValue
**验证步骤**:
1. Reload extension
2. 确保浏览器中已登录千问（在普通标签页中）
3. 打开 ChatFree 页面，观察千问是否：
   - 不再弹出登陆框
   - 不再刷新
   - 能正常发送消息和接收回复
4. 查看 background debug log 确认 cookie 注入状态
**结果**: 
- 千问 cookie 注入有效，停止闪烁，正常显示已登录状态
- **副作用**：DNR 规则是全局的，影响了普通标签页的 Cookie header
- 在普通标签页登录/登出时，DNR 规则注入的是旧 cookie，导致普通标签页 cookie 被覆盖
- 需要限制 cookie 注入仅在扩展页面打开时激活

### 实验 7: Port-based cookie 注入（仅扩展页面激活时）
**日期**: 2026-05-18
**假设**: DNR 规则全局生效影响了正常浏览。通过 port 长连接限制 cookie 注入只在 ChatFree 页面打开时激活，关闭时自动移除规则。
**方法**:
1. `background.js` — cookie 注入改为 port-based
   - 通过 `chrome.runtime.connect({name:'chatfree-app'})` 激活
   - port 断开时自动 `updateSessionRules({removeRuleIds})`
   - `resourceTypes` 仅限 `sub_frame` + `xmlhttprequest`（移除 main_frame/script）
   - 30s 定时 + cookie.onChanged 双重刷新
   - 支持多个 app 页面并存（port 计数）
2. `app.js` — 加载时 `chrome.runtime.connect({name:'chatfree-app'})`，关闭时自动断开
3. `nav-guard.js` — 移除 `beforeunload` 的 `returnValue`（不再弹窗）
**代码变更**:
- `background.js` — cookie 注入改为 port-based 生命周期
- `app.js` — 新增 port 连接
- `modules/nav-guard.js` — 移除 beforeunload returnValue
**验证步骤**:
1. Reload extension
2. 普通标签页访问千问 → 应不受影响
3. 打开 ChatFree → 千问应显示已登录
4. 在其他标签页重新登录 → ChatFree 刷新后在 30s 内更新
5. 关闭 ChatFree → 普通标签页不受影响
